## 1. decode 为什么这么难提速

回忆两个已经学过的事实,它们合起来制造了 decode 的困境:

- **串行依赖**:自回归生成,第 t+1 个 token 必须等第 t 个算完才能开始(要把它喂回去)。这是**算法层面的串行**,没法靠并行硬解。
- **带宽受限**(Lesson 1):每生成 1 个 token 要把整个模型权重从显存读一遍,但只算了 1 个 token,GPU 算力大量空转。

batching 解决的是"**多个请求**之间"的浪费(把别人的 token 凑进来一起算)。但如果你只有**一个请求**、或者就是想让**这一个请求更快出结果**(降低单请求延迟,TPOT),batching 帮不上忙——它提的是吞吐,不是单请求延迟。

关键观察来了:

> **decode 每一步,GPU 其实"算力有余、带宽吃紧"。** 我们花了昂贵的带宽把权重搬上片,却只算了 1 个 token。**那能不能在一次权重搬运里,多验证几个 token?** 这正是投机解码的突破口——它把 decode 从"带宽受限的逐个挤"变成"一次前向验证一批",把闲置的算力换成吞吐。

这和你做大数据优化的直觉一致:既然搬运(IO)是瓶颈、计算有余,那就在一次搬运里多干点计算活,提高"每次搬运的产出"。

## 2. 核心思想:草稿员 + 审稿员

投机解码用两个模型:

- **draft model(草稿模型)**:一个小而快的模型(如 Llama-7B 配 Llama-68M,或同族小尺寸)。它便宜,但质量差些。
- **target model(目标模型)**:你真正想用的大模型,质量高但慢。

工作流程(一轮):

```
第 1 步:draft 连续猜 k 个 token(便宜,串行跑小模型 k 次)
   大模型上文 "The weather today is"
   小模型猜: "sunny" "and" "warm" "with"   (k=4 个草稿 token)

第 2 步:大模型"一次前向"并行验证这 k 个草稿(关键!)
   把 [is, sunny, and, warm, with] 一起喂给大模型,一次前向就拿到
   大模型在每个位置"本应输出什么"的概率分布。
   注意:这是 1 次大模型前向,却覆盖了 k 个位置 —— 因为它们已经都知道了(草稿给的),
   可以像 prefill 那样并行算,不必逐个串行!

第 3 步:从左到右比对,接受 / 拒绝
   位置1 sunny:大模型也大概率认可 → 接受 ✓
   位置2 and  :大模型认可          → 接受 ✓
   位置3 warm :大模型不认可         → 拒绝 ✗,用大模型的分布在这里重采样一个正确 token
   位置4 with :作废(前面已经断了)
```

一图概括两者的时间线对比:

```
纯自回归(大模型逐个生成,每个 token 一次大模型前向):
大模型 ██──██──██──██──██──██   (6 个 token = 6 次大模型前向,慢)

投机解码(小模型猜 4 个,大模型一次验证):
小模型 ▪▪▪▪          ▪▪▪▪        (便宜,几乎不计成本)
大模型     ████          ████     (1 次大模型前向验证 4 个;接受 3 个 → 这轮赚 3+1 个 token)
       └ 一轮 ┘
```

> **关键结论:投机解码用"小模型的廉价串行猜测 + 大模型的一次并行验证",把多个 token 的产出压缩进一次大模型前向。** 大模型前向次数从"等于生成 token 数"降到"等于轮数",而每轮能产出多个被接受的 token——这就是加速来源。它**不增大 batch**,而是减少"昂贵前向"的次数。

## 3. 为什么无损?接受/拒绝采样的精妙

最反直觉、也最关键的一点:**投机解码生成的结果,和大模型自己逐个生成的结果,在统计分布上完全一致——它是无损加速,不是近似。**

很多人第一反应是"用小模型猜,质量肯定打折"。错。秘密在**接受/拒绝采样(speculative / rejection sampling)** 这套数学,它保证了:**无论小模型多烂,最终采出的 token 都严格服从大模型的概率分布。**

机制(设某位置小模型给的分布是 \(q\),大模型给的是 \(p\),小模型采出了 token \(x\)):

```
若 p(x) >= q(x):    无条件接受 x          (大模型比小模型更"看好"这个 token,放心收)
若 p(x) <  q(x):    以概率 p(x)/q(x) 接受;
                    否则拒绝,并从"修正分布" (p - q)+ 归一化后重采样一个新 token
```

- `(p - q)+` 表示对每个 token 取 \(\max(p-q, 0)\) 再归一化——它专门补上"大模型想要、但小模型给少了"的那部分概率。
- 这套接受 + 修正重采样的组合,**数学上可证明**:最终 token 的分布恰好等于 \(p\)(大模型分布)。

> **关键结论:接受/拒绝采样让"用小模型猜"变成数学上无损——输出分布严格等于大模型。** 小模型的好坏只影响**速度**(猜得准 → 接受得多 → 快),**不影响质量**。这是投机解码能被放心用于生产的根本原因。

一个直觉解释:小模型猜对的时候(大模型也认可),我们白赚一个 token;小模型猜错的时候,接受/拒绝那一步会"纠偏",用大模型的真实意图覆盖掉错误猜测。无论如何,留下的 token 都是大模型"会同意"的。

(贪心解码 greedy 是这套机制的特例:此时接受规则退化成"小模型猜的 token 是否等于大模型 argmax",相等则接受,否则用大模型的 argmax 替换。)

## 4. 加速比由什么决定:算一笔账

投机解码不是免费午餐,加速比取决于三个量,理解它们才会调:

- **接受率 α(alpha)**:大模型平均接受小模型草稿的比例。α 越高,每轮白赚的 token 越多。α 主要由"小模型和大模型有多像"决定。
- **猜测长度 k**:每轮小模型猜几个。k 越大潜在收益越大,但 α 不够高时,后面的猜测大概率被拒、白白浪费小模型算力。
- **成本比 c**:小模型单步前向成本 / 大模型单步前向成本(如 0.1~0.2)。小模型相对越便宜,投机越划算。

每轮的期望产出(接受 token 数)在 α<1 时约为 \(\frac{1-\alpha^{k+1}}{1-\alpha}\)(几何级数),每轮成本 ≈ 1 次大模型前向 + k 次小模型前向。把它们一除就是加速比。

`code/speculative_decoding_sim.py` 把这笔账模拟出来了。运行:

```bash
cd code
python speculative_decoding_sim.py
```

参考输出(小模型成本为大模型的 15%):

```
k      alpha    tokens/大模型前向    等效加速比
1      0.5      1.49               1.30x
4      0.5      1.92               1.20x
8      0.5      1.97               0.90x      ← 注意!变慢了

1      0.7      1.70               1.47x
4      0.7      2.75               1.72x
8      0.7      3.17               1.44x

1      0.9      1.90               1.65x
4      0.9      4.06               2.54x
8      0.9      6.14               2.79x      ← 高接受率 + 大 k,接近 3x
```

从这张表读出三条规律,比记数字重要:

- **α 越高,加速越猛**:α=0.9 时 k=8 能到约 2.8×;α=0.5 时怎么调都很勉强。**所以投机解码的成败首先在"小模型像不像大模型"。**
- **k 不是越大越好**:看 α=0.5、k=8 那行——**加速比 0.90×,反而比不投机还慢!** 因为接受率低时,猜的 8 个大半被拒,小模型那 8 次前向纯属浪费。k 要和 α 匹配。
- **存在最优 k**:α 固定时,加速比先升后降(α=0.7 时 k=4 比 k=8 更好)。实际系统常**动态调整 k**。

> **关键结论:投机解码的加速比 ≈ f(接受率 α, 猜测长度 k, 成本比 c),核心是 α。** α 高(小模型好)且 k 适中时收益最大;α 低时盲目加大 k 会因"白猜"而**变慢**。这是面试高频追问点。

## 5. 工程变体与适用场景

投机解码这几年衍生出一堆变体,知道脉络即可:

- **独立草稿模型(标准投机解码)**:用一个单独的小模型当 draft。问题:要额外部署、加载一个模型,且小模型要和大模型"同源同 tokenizer"。
- **Medusa**:不用单独小模型,而是在大模型上加几个**额外的预测头(heads)**,一次前向同时猜出后面几个位置。省掉了独立草稿模型的部署麻烦。
- **EAGLE / EAGLE-2/3**:目前效果最好的一类,在特征层面做轻量自回归草稿,接受率高,加速比常达 2-4×,vLLM 已支持。
- **Lookahead / 基于 n-gram 的草稿**:用历史文本的 n-gram 直接当草稿(对代码、重复性强的文本特别有效),零额外模型。
- **Prompt lookup decoding**:从 prompt 里直接找重复片段当草稿,适合摘要、RAG 这类"输出大量复制输入"的场景。

什么时候投机解码划算 / 不划算:

| 场景 | 是否划算 | 原因 |
|---|---|---|
| **低并发 / batch 小、想降单请求延迟** | ✅ 很划算 | 此时 GPU 算力大量闲置,正好用来验证草稿;TPOT 显著下降 |
| 输出可预测性高(代码、格式化、引用原文) | ✅ 划算 | 小模型/n-gram 容易猜中,α 高 |
| **高并发 / batch 已经很大** | ❌ 常不划算 | 大 batch 下 GPU 算力已被打满,没有"闲置算力"留给验证,投机反而增加开销 |
| 小模型和大模型差异大(α 低) | ❌ 不划算 | 接受率低,白猜浪费,可能更慢(见上表) |

> **关键结论:投机解码主要是一种"低负载下用闲置算力换单请求延迟"的技术。** 它和 continuous batching 是**互补**的:后者在高并发下提吞吐,前者在低并发下降延迟。两者解决的是不同象限的问题。理解这点,你才知道什么时候该开它。

<details>
<summary>参考答案(想完再看)</summary>

1. batching 是把**多个请求**的 token 凑一起算,提升的是整机**吞吐**,但单个请求仍是逐 token 串行,延迟不变。投机解码从"减少大模型前向次数"入手:一次大模型前向验证多个草稿 token,把单请求的多个 token 压进一次前向,直接降低单请求 decode 延迟(TPOT)。

2. 因为接受/拒绝采样在数学上保证:接受规则 + 被拒后从修正分布 `(p-q)+` 重采样,组合起来使最终 token 的分布严格等于大模型分布 p。小模型只决定"猜得准不准"→ 接受率 α → **速度**,不影响最终分布 → 不影响**质量**。

3. `p(x) >= q(x)` 说明大模型对这个 token 比小模型还看好,当然该收;`p(x) < q(x)` 说明小模型"高估"了它,所以只按 `p(x)/q(x)` 的比例接受,把多出来的概率"退回去"。被拒后用 `(p-q)+`(大模型想要但小模型给少的部分)重采样,是为了精确补偿被接受步骤造成的分布偏差,从而整体上严格还原 p;直接用 argmax 只在 greedy 特例下等价,一般采样下会破坏分布。

4. α=0.5 时,草稿第 1 个之后被接受的概率快速衰减(0.5、0.25、0.125...),猜 8 个里后面六七个几乎必被拒,但小模型仍实打实跑了 8 次前向,这些算力全浪费,且每轮固定成本被摊薄得不够。应该**减小 k**(α=0.5 时 k=1 反而最优),或提高 α(换更像大模型的草稿模型)。

5. 夜里低并发时 GPU 算力闲置,**开投机解码**降低单请求延迟、改善体验;白天高并发时 batch 已经把算力打满,投机的"额外验证"无算力可用、反而拖累,应**关掉投机、靠 continuous batching 提吞吐**。即按负载动态切换:低负载用投机降延迟,高负载用大 batch 提吞吐。

6. 优点:不用部署/加载独立小模型,省显存和运维,且预测头与大模型共享主干、tokenizer 天然一致;一次前向就出草稿,流程更简单。潜在缺点:预测头要额外训练/微调,接受率通常不如精心训练的独立草稿或 EAGLE 高,且给大模型本身增加了一点结构和计算负担。

## 小结

- decode 难提速的根因:**串行依赖 + 带宽受限**;batching 只提吞吐,救不了单请求延迟。
- 投机解码 = **小模型 draft(廉价串行猜 k 个)+ 大模型 verify(一次并行验证)**,把多个 token 压进一次大模型前向。
- **接受/拒绝采样**让它**无损**:输出分布严格等于大模型,小模型质量只影响速度不影响质量。
- 加速比 ≈ f(**接受率 α**, **猜测长度 k**, **成本比 c**),核心是 α;α 低时盲目加大 k 会**变慢**。
- 变体:Medusa、EAGLE、n-gram/prompt-lookup。它是**低并发降延迟**的利器,和 continuous batching(高并发提吞吐)**互补**。
