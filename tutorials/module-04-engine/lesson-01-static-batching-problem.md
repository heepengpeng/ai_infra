## 1. 先回到原点:为什么要 batching

回忆 Lesson 1(M1)那句话:**GPU 是吞吐优先架构**,几千个 ALU 等着喂数据。再回忆 decode 阶段的本质——**带宽受限**:每生成一个 token,要把整个模型的权重从显存读一遍,但只算了一个 token 的乘加。

把这两件事放一起,一个惊人的结论就出来了:

> **decode 阶段单个请求时,GPU 算力几乎全在空转。** 你花了昂贵的带宽把 7B 权重搬上片,却只服务了一个 token 的计算。

类比你熟悉的分布式系统:这就像启动一个 Spark Executor、加载了几百 MB 的 broadcast 变量,结果只处理了一条记录就关掉。搬运成本(读权重)被摊在了一条数据上,**摊销率极差**。

batching 的核心思想就是**摊销**:既然权重已经搬上片了,为什么不顺手多算几个请求?

```
单请求 decode 一步:
  读 7B 权重(慢,~14GB 带宽搬运) → 算 1 个 token 的 GEMM(快,几乎瞬间)
  ───────────────────────────────────────────────────────
  权重搬运成本 / 服务的 token 数 = 14GB / 1 = 14GB per token  ❌ 极差

batch=32 decode 一步:
  读 7B 权重(还是那一遍!) → 算 32 个 token 的 GEMM(批量矩阵乘,GPU 主场)
  ───────────────────────────────────────────────────────
  权重搬运成本 / 服务的 token 数 = 14GB / 32 ≈ 0.44GB per token  ✅
```

**关键结论:在 decode 阶段,batch 几乎是"免费"地提升吞吐**——权重只读一遍,却服务了 32 个请求。从矩阵运算视角看,单请求的矩阵-向量乘(GEMV,带宽受限)变成了矩阵-矩阵乘(GEMM,能吃满算力)。这就是所有推理引擎都拼命想把 batch 做大的根本原因。

> 记住这句话:**推理引擎的吞吐量,本质上是一场"如何把 batch 尽可能塞大、塞满"的战争。** 本模块从头到尾都在打这场仗。

## 2. 静态 batching 长什么样

既然 batch 这么香,最朴素的做法就是:**攒一批请求,一起从头跑到尾。** 这就是静态批处理(static batching),也叫 naive batching。

它的工作流程:

```
                    ┌──── 一个静态 batch 的生命周期 ────┐
请求到达 → 攒够 N 个 → 一起 prefill → 一起 decode 到全部结束 → 一起返回 → 释放
           (或超时)                  ↑
                                每个 step 同时给 batch 里所有请求各生成 1 个 token
```

代码骨架大概是这样(只为说明结构,不是能跑的引擎):

```python
import logging

logger = logging.getLogger(__name__)


def static_batch_generate(model, requests, max_new_tokens):
    # 一批请求一起进来,直到全部结束才返回。这就是"静态"的含义。
    batch = pad_to_same_length(requests)  # 关键:必须 padding 对齐,见第 3 节
    kv_cache = model.prefill(batch)
    outputs = [[] for _ in requests]

    for step in range(max_new_tokens):
        next_tokens = model.decode_step(batch, kv_cache)
        for i, tok in enumerate(next_tokens):
            outputs[i].append(tok)
        # 注意:即使某个请求已经吐出了 EOS,这个循环也不会把它踢出去。
        # 它会继续占着 batch 里的一个槽位,陪着别人空跑。这是病根之一。
        if all_finished(outputs):
            break
    return outputs
```

静态 batching 隐含了**两条致命假设**:

- **假设一:一个 batch 里的请求,长度差不多。** 这样 padding 浪费才小。
- **假设二:一个 batch 里的请求,会差不多同时结束。** 这样才不会有人空等。

现实里这两条假设**几乎永远不成立**。下面两节就来拆穿它们。

---

## 3. 病根一:长度不齐 → padding 浪费

GPU 上做 batch 运算,要求一个 batch 里所有样本的张量形状**必须对齐**(同一个矩阵乘里,序列维度得一样长)。但用户的请求长度千差万别:

```
请求 A: "翻译这句话"                          → prompt 5 token
请求 B: "把下面这篇 2000 字的文章总结一下:..."  → prompt 1800 token
请求 C: "1+1=?"                              → prompt 4 token
```

要凑成一个 batch,只能**按最长的对齐**,短的用无意义的 `<pad>` 填满:

```
        token 位置 →  0    1    2   ...              1799
请求 A  [t t t t t pad pad pad pad ............... pad]   ← 5 个真 token,1795 个 pad!
请求 B  [t t t t t  t   t   t   t  ............... t  ]   ← 1800 个真 token,刚好占满
请求 C  [t t t t pad pad pad pad pad ............. pad]   ← 4 个真 token,1796 个 pad!
        └──────────────── 全部按 1800 对齐 ────────────────┘
```

这些 `<pad>` 位置照样要参与矩阵运算(算完再用 mask 丢弃),**纯属空烧算力和显存**。算一笔账:

| 请求 | 真实 token | padding token | 浪费比例 |
|---|---|---|---|
| A | 5 | 1795 | 99.7% |
| B | 1800 | 0 | 0% |
| C | 4 | 1796 | 99.8% |
| **合计** | **1809** | **3591** | **约 66% 算力烧在 padding 上** |

> **关键结论:把长短悬殊的请求硬凑成一个静态 batch,padding 可能吃掉一大半算力。** batch 越大、长度越分散,浪费越离谱。

你可能会想:那我"按长度分桶(bucketing)"不就行了?把长度相近的放一起。这是真实存在的缓解手段,但它有代价:分桶意味着**等待**——为了凑齐一个"长度都在 1700~1800"的桶,可能要等很久,牺牲了延迟(TTFT 飙升)。这又回到了那场战争:**吞吐 vs 延迟的拉锯**。分桶治标不治本。

---

## 4. 病根二:同生共死 → 木桶效应拖垮利用率

这是静态 batching 更致命的问题,而且和 LLM 的特性死磕。

LLM 生成是**自回归**的,每个请求生成多少 token **事先不知道**——它自己吐 EOS 才停。于是一个 batch 里:

```
        生成进度(每个 step 各请求生成 1 token)→
请求 A  ████ EOS                                      (生成 4 个就结束了)
请求 B  ████████████████████████████████████ EOS      (生成 200 个,话痨)
请求 C  ██████ EOS                                     (生成 6 个)
请求 D  █████████ EOS                                  (生成 9 个)
        ↑
        step 0                                  step 199
```

静态 batching 的规矩是**同生共死**:整个 batch 必须等到**最慢的那个请求(B)**结束,才能一起返回、释放资源。于是:

- A 在 step 4 就吐完了 EOS,但它的槽位**不能给新请求**。从 step 5 到 step 199,A 这一行一直在 batch 里**陪跑空算**(算出来的 token 直接丢弃)。
- C、D 同理,大部分时间在空转。

用一张利用率图看就触目惊心(■ = 真实有效计算,· = 空跑浪费):

```
        step→  0   4    6    9                    199
请求 A        ■■■■····························空跑···· (从 step5 起全废)
请求 B        ■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■ (一直在干活)
请求 C        ■■■■■■··························空跑····
请求 D        ■■■■■■■■■····················空跑····
              └── 整个 batch 的有效计算占比可能不到 30% ──┘
```

这就是**木桶效应 / 长尾拖累**:一个话痨请求,把整批短请求全拖住,GPU 大量算力在给已经结束的请求"空跑"。

> **关键结论:静态 batching 下,batch 的吞吐被最长的请求绑架,GPU 利用率随请求长度方差增大而暴跌。** 而 LLM 输出长度的方差恰恰非常大(有人问"1+1",有人让你写一篇论文)。

熟悉调度的你一定眼熟:这就是经典的 **HOL(队头阻塞,Head-Of-Line blocking)**。一个慢任务卡住整条流水线,后面排队的新请求只能干等——哪怕 GPU 此刻有大把空闲算力。在 MapReduce / Spark 里这叫 **straggler(掉队者)拖垮整个 stage**,你应该再熟悉不过。静态 batching 把"任务"绑成了一个不可分割的批,等于主动放弃了细粒度调度的能力。

## 5. 还有一层:prefill 和 decode 的收益完全不同

最后埋一个关键认知,它是后面所有调度设计的基础。batching 在两个阶段的收益**完全不一样**:

| 阶段 | 计算特征 | 单请求时瓶颈 | batching 收益 |
|---|---|---|---|
| **prefill**(处理 prompt) | 一次并行算完整个 prompt 的所有 token,矩阵乘维度大 | 本来就**算力受限**,GPU 已经吃得比较饱 | 收益有限,甚至可能因 padding 反受其害 |
| **decode**(逐 token 生成) | 每步只算 1 个新 token,矩阵-向量乘 | **带宽受限**,算力大量空转 | 收益巨大,batch 几乎免费提吞吐 |

直觉解释:

- **prefill** 像是一次性处理一大块数据(prompt 几百上千 token 一起算),GPU 本来就有活干,batch 主要带来 padding 麻烦。
- **decode** 像是挤牙膏,一次一个 token,GPU 严重吃不饱,这时候把多个请求的"这一个 token"凑一起算,才是雪中送炭。

> **关键结论:batching 的红利主要在 decode 阶段兑现。** 这解释了为什么后面 continuous batching 的核心是**在每个 decode step 动态重组 batch**,以及为什么 prefill 和 decode 常常要分开调度(甚至分开部署,即 prefill-decode disaggregation)。

把这条记住,Lesson 2 你会看到:continuous batching 正是抓住"decode 可以逐 step 灵活拼 batch"这个特性,把上面两个病根一起治了。

## 6. 小结:静态 batching 的三宗罪

把这一课压缩成一张问题清单,它就是后续每一课的"靶子":

```
静态 batching 三宗罪              后续哪一课来治
─────────────────────────────────────────────────────
① padding 浪费(长度不齐)    →   Lesson 2 continuous batching(逐 step 重组,无需全局 padding)
② 同生共死 / HOL 阻塞        →   Lesson 2 continuous batching(请求随时进出)
③ 显存被 KV Cache 整块预占   →   Lesson 3 PagedAttention(按需分页,消碎片)
```

(第 3 条本课只点到为止:静态 batching 还要为 batch 里每个请求**按最大长度预留 KV Cache 显存**,即使它实际只生成几个 token——这又是一笔巨大浪费,留给 Lesson 3 详细拆解。)

<summary>参考答案(想完再看)</summary>

1. 最长 800,对齐后每个请求都占 800 个槽位,共 8×800 = 6400。真实 token = 10+12+800+11+9+13+10+8 = 873。浪费 = (6400−873)/6400 ≈ **86.4%**。说明只要 batch 里混进一个长 prompt,绝大部分 prefill 算力都烧在 padding 上,长度方差是元凶。

2. 静态 batching 必须等最长的(300)结束,所以要跑 **300 个 step**。有效 token = 5+6+300+4+7+5+6+5 = 338。实际占用的槽位 = 8×300 = 2400。有效比例 ≈ 338/2400 ≈ **14%**。也就是说约 86% 的 decode 计算在给已结束的请求空跑。

3. 分桶要"攒齐一个长度相近的桶"才能开跑,这需要**等待**,直接推高 TTFT(首 token 延迟),在低/中负载下尤其难凑齐桶;而且桶的边界永远会有跨界请求。它只是降低了 padding 的方差,没解决"同生共死"和动态进出的问题。牺牲的是**延迟**(以及负载不均时的吞吐)。

4. batch=1 确实消除了 padding 和木桶效应,但它**放弃了 batching 的全部吞吐红利**:decode 阶段权重每步只服务 1 个 token,GPU 算力几乎全空转,吞吐量低到无法支撑生产流量、单位 token 成本极高。这是把问题从"浪费在 padding/空跑"换成了"浪费在带宽摊销率极差",更糟。

5. "同生共死"对应批处理里的 **straggler(掉队者)拖垮整个 stage**、以及 **HOL 队头阻塞**——一个慢任务卡住整批。continuous batching 借鉴的正是**流处理 / 细粒度调度**思想:把"批"拆成可逐步调度的单元(以 step 为粒度),完成的及时退出、新来的随时加入,类似流式系统里记录级的连续处理 + 动态资源回收。

## 小结

- batching 的本质是**摊销权重搬运成本**:decode 阶段带宽受限,batch 几乎"免费"提吞吐——这是引擎拼命做大 batch 的根本动机。
- **静态(naive)batching** = 攒一批、一起从头跑到尾,隐含"长度相近 + 同时结束"两条几乎不成立的假设。
- 三宗罪:① **padding 浪费**(长度不齐,可吃掉大半算力)② **同生共死 / HOL 阻塞**(被最长请求绑架,利用率暴跌)③ **KV Cache 整块预占**(留待 Lesson 3)。
- batching 红利**主要在 decode 阶段**;这决定了后续调度都围绕"逐 step 灵活重组 decode batch"展开。
