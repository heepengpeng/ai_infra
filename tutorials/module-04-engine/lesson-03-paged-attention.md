## 1. 先算账:KV Cache 到底有多大

回忆 Module 3:每个 token 在每一层都要缓存它的 Key 和 Value 向量,这样 decode 时不用重算历史。一个 token 的 KV Cache 大小:

```
单 token KV 字节数 = 2(K 和 V) × 层数 L × 注意力头数 × head_dim × dtype字节数
                  = 2 × L × hidden_size × dtype字节数   (hidden_size = 头数 × head_dim)
```

以 **Llama-2-13B**(L=40,hidden_size=5120,FP16 即 2 字节)为例,单 token:

```
2 × 40 × 5120 × 2 = 819,200 字节 ≈ 0.78 MB / token
```

一个 2048 token 的序列,光 KV Cache 就要 **约 1.6 GB**。一张 A100-40G 在装完 13B 权重(约 26GB)后,剩下十几 GB 显存全靠 KV Cache 来塞并发请求。

> **关键结论:KV Cache 的大小随 "并发请求数 × 每个请求的序列长度" 线性增长,它——而不是权重——决定了你能开多大 batch。** 把 KV Cache 管好,就是把吞吐做大。论文里 vLLM 团队实测:朴素管理下,**真正有用的 KV Cache 显存利用率可能低到 20%~40%**,剩下全浪费了。下一节就看浪费在哪。

## 2. 传统做法的病:连续预留 → 三种浪费

朴素的引擎(如早期 HF、FasterTransformer)怎么存一个请求的 KV Cache?**给它分配一整段连续显存,大小按"这个请求最多可能生成的长度(max_seq_len)"预留。**

这和 C 语言里 `malloc(max_size)` 一个大数组一模一样。问题也一模一样,而且三种碎片全占了:

```
假设 max_seq_len = 2048,给每个请求预留一整条 2048 的连续显存:

请求 A(实际只生成 100 token):
┌────────────────────────────────────────────────────────┐
│ ███(100 真实 KV) ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░ │  ← 1948 个槽位预留着白占,直到请求结束
└────────────────────────────────────────────────────────┘
  实际用 5%                预留浪费 95%(internal + reservation)
```

三种浪费,逐个对号入座(论文里的术语,面试常考):

- **预留浪费(reserved)**:为"将来可能用到"而预留、但当前还没用上的部分(上图 A 的 1948 槽)。请求没结束就一直占着,别人用不了。
- **内部碎片(internal fragmentation)**:因为按 max_seq_len 预留,但请求实际远没那么长,多分的部分永远用不到。这是最大头。
- **外部碎片(external fragmentation)**:不同请求预留的块大小不一,请求结束释放后,显存被切成一堆"不连续的小空洞"。新请求要一整条连续显存,即使空洞总量够,也凑不出一条连续的来,**塞不进去**——典型的"内存够但分不出来"。

> **关键结论:要求"每个请求一整段连续显存 + 按最大长度预留",同时引发了内部碎片、外部碎片和预留浪费,把宝贵的 KV Cache 显存浪费掉一大半。** 你在 C/OS 课里见过的 malloc 碎片问题,在 KV Cache 上原样重演。

而 OS 几十年前就解决过一模一样的问题。怎么解决的?**分页。**

## 3. 顿悟时刻:这不就是虚拟内存吗

回忆操作系统:进程也想要"一大段连续的内存",但物理内存有限又零碎。OS 的解法是**虚拟内存分页**:

- 把物理内存切成固定大小的**页帧(page frame)**(如 4KB)。
- 进程看到的是连续的**虚拟地址**,但背后由**页表(page table)**映射到**任意分散**的物理页帧。
- 进程**按需**申请页(用到才分配),不用时归还。

PagedAttention 把这套机制**逐字搬到 KV Cache 上**,术语一一对应:

| 操作系统(虚拟内存) | PagedAttention(KV Cache) |
|---|---|
| 物理内存 | GPU 显存里的 KV Cache 区 |
| 页帧 page frame(固定大小) | **KV block**(固定存 N 个 token 的 KV,vLLM 默认 N=16) |
| 虚拟地址空间(连续) | 请求看到的"逻辑上连续的 KV 序列" |
| 页表 page table | **block table(块表)** |
| 虚拟页号 → 物理页帧号 | **逻辑块号 → 物理块号** |
| 按需分页(demand paging) | token 生成到需要新块时才分配 |
| 共享页(shared library) | **prefix / beam 共享 KV 块** |
| 写时复制 copy-on-write | **CoW**(共享块要写入时再复制) |

> **核心思想一句话:KV Cache 在物理上不必连续。** 把它切成固定大小的小块(block),散落在显存各处,用一张 block table 把"请求眼中连续的 token 序列"映射到"物理上分散的块"。请求按需申请块、结束归还块。

这一下三种浪费全治了:

- **内部碎片**:只剩"最后一个没填满的块"那点零头(最多 block_size−1 个槽,vLLM 里 ≤15 个 token),从 1948 槽降到 ≤15 槽。
- **外部碎片**:**彻底消失**。因为所有块大小一样,任何空闲块都能给任何请求用,不存在"凑不出连续段"。
- **预留浪费**:**消失**。用一块申请一块,不预留。

## 4. block table 详细图解(本课重点)

把抽象讲具体。设 `block_size = 4`(每块存 4 个 token 的 KV;真实 vLLM 是 16,这里用 4 方便画图)。

**初始:物理 KV Cache 区 = 一池固定大小的块**,编号 0~7,初始全空闲:

```
物理 KV Cache 区(显存里一整块,预先切好的 8 个等大块):
┌─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┐
│ blk0│ blk1│ blk2│ blk3│ blk4│ blk5│ blk6│ blk7│
│ 空  │ 空  │ 空  │ 空  │ 空  │ 空  │ 空  │ 空  │
└─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┘
空闲块池: [0,1,2,3,4,5,6,7]
```

**请求 A 来了,prompt 有 6 个 token**(`The cat sat on the mat`)。需要 ⌈6/4⌉ = 2 个块。分配器给它两个**任意**空闲块(比如 7 和 5,物理上不连续没关系):

```
请求 A 的逻辑视图(它以为自己有连续的 6 个 token KV):
逻辑块号:   [  逻辑块0  ][  逻辑块1  ]
token:      The cat sat on   the mat _ _
            └─ 满(4个)─┘   └ 2个+2空 ┘

请求 A 的 block table(逻辑块号 → 物理块号):
┌──────────┬──────────┐
│ 逻辑块0   │ 逻辑块1   │
│   → 物理7 │   → 物理5 │
└──────────┴──────────┘

物理区现状:
┌─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┐
│ blk0│ blk1│ blk2│ blk3│ blk4│ blk5│ blk6│ blk7│
│ 空  │ 空  │ 空  │ 空  │ 空  │A逻1 │ 空  │A逻0 │
└─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┘
空闲块池: [0,1,2,3,4,6]
```

**A 开始 decode,逐个生成新 token**。逻辑块1 还有 2 个空位(`mat` 后面还能放 2 个),先填满它:

```
生成 token #7、#8 → 填进逻辑块1 剩余空位,无需新块:
逻辑块1: the mat w1 w2   ← 满了
```

**继续生成 token #9**:逻辑块1 已满,**按需分配新块**(demand paging)。分配器给一个空闲块(比如 0):

```
请求 A 的 block table 增长:
┌──────────┬──────────┬──────────┐
│ 逻辑块0   │ 逻辑块1   │ 逻辑块2   │
│   → 物理7 │   → 物理5 │   → 物理0 │  ← 生成到需要时才追加,绝不预留
└──────────┴──────────┴──────────┘
                          ↑ 逻辑块2 现在只放了 1 个 token,内部碎片最多 3 个槽
```

**这就是 PagedAttention 的全部精髓**:请求只维护一张 block table,生成到哪、要新块了,就向分配器要一块(任意物理位置),记进表里。attention 计算时,kernel 通过 block table 找到每个逻辑位置对应的物理块去读 KV(这就是它要专门写一个 "paged" attention kernel 的原因——普通 attention 假设 KV 连续,分页后 KV 散在各块,kernel 必须按块表间接寻址)。

**请求 A 结束**:把它 block table 里的物理块(7、5、0)全部归还空闲池,这些块立刻能给别人用——**没有外部碎片,因为块大小统一**。

```
A 结束后空闲块池: [0,1,2,3,4,5,6,7]  ← 全部回归,任何块都能复用
```

> 对照第 2 节那张"连续预留"图:同样的请求,连续预留要白占 2048−9 个槽直到结束;分页只占了实际用到的块,内部碎片 ≤ block_size−1。**这就是 vLLM 把 KV 显存利用率从 ~20-40% 拉到 ~90%+ 的机制。**

## 5. 额外红利:共享 KV 块(分页才能做的事)

分页不只是省,它还**解锁了共享**——这是连续预留方案根本做不到的。因为块是独立的最小单位,多个请求可以让自己 block table 的某些表项**指向同一个物理块**(像多个进程映射同一个共享库页)。

**红利一:prefix sharing(前缀共享)。** 很多请求有相同的前缀:同一个超长 system prompt、few-shot 示例、RAG 拼进去的同一段文档。它们的这段前缀 KV **完全一样**,没必要各存一份:

```
请求 B、C、D 都用同一段 system prompt(占 2 个块的 KV):

请求 B 的 block table: [→物理3][→物理6][→自己的块...]
请求 C 的 block table: [→物理3][→物理6][→自己的块...]   ← 前两块指向同一物理块!
请求 D 的 block table: [→物理3][→物理6][→自己的块...]

物理块 3、6 只存一份 system prompt 的 KV,被 3 个请求共享。
引用计数:物理块3.refcount = 3
```

prefill 时这段共享前缀**只需算一次**(prefix caching),省算力又省显存。长 system prompt + 高并发场景,收益巨大。

**红利二:beam search / 并行采样共享。** beam search 里多个候选 beam 共享同一段历史;一个 prompt 要求生成多个回答(`n>1`)时,几个输出共享同一段 prompt KV。分页让这些共享天然成立。

**配套机制:copy-on-write(写时复制)。** 共享块只读时大家共用;一旦某个请求要往共享块**写入**新内容(比如两个 beam 在某点分叉,要写不同的 token),就**复制一份**该块给它单独改,原块不动。和 OS 的 CoW、`fork()` 一模一样。引用计数(refcount)决定一个物理块何时能真正回收:**refcount 归零才释放**。

> **关键结论:分页不仅消除碎片,还把"共享只读 KV"变成可能——前缀共享、beam 共享、prefix caching,这些 vLLM 的高级特性全建立在 block table + 引用计数 + CoW 之上。** 没有分页,这些都无从谈起。

## 6. 动手:模拟块表分配

`code/paged_kv_cache_sim.py` 用纯 Python 模拟了块分配器(`BlockAllocator`)、序列块表(`Sequence`)、按需分配、释放、引用计数共享。它不做真实 attention,只演示**显存块的分配/释放/共享机制**。

两个核心数据结构:

```python
class BlockAllocator:           # 物理块池,类比 OS 物理页帧管理
    def allocate(self) -> int   # 取一个空闲物理块
    def share(self, block)      # 共享:引用计数 +1
    def free(self, block)       # 归还:引用计数归零才真回收

class Sequence:                 # 一个请求,持有自己的块表
    block_table: list           # 索引=逻辑块号, 值=物理块号
    def append_tokens(n, alloc) # 生成 n 个 token,按需申请新块
```

运行:

```bash
cd code
python paged_kv_cache_sim.py
```

参考输出(`block_size=16`,100 个物理块,max_len=512):

```
物理块总数=100,每块=16 token,max_len=512
静态预留:每请求占 32 块 -> 最多容纳 3 个请求
分页按需:每请求实际 40 token -> 容纳了 33 个请求(同样 100 块)
提升约 11.0x

--- 前缀共享演示 ---
请求 A 前缀占用物理块: [99, 98],剩余空闲块=98
请求 B 复用前缀(零额外显存),剩余空闲块=98
共享块 99 的引用计数=2
A 释放后,共享块 99 引用计数=1(仍被 B 持有,未回收)
```

读懂它:静态预留按 max_len=512 给每个请求死占 32 块,只能塞 3 个请求;分页按实际长度(40 token,3 块)分配,同样 100 块能塞 33 个,**11× 提升**——这就是 KV 显存利用率的差距。前缀共享演示里,B 复用 A 的前缀块零额外显存,A 释放后共享块因 refcount 仍 >0 而不被回收,正是 CoW/引用计数的安全保证。

## 小结

- **KV Cache 随 "并发数 × 序列长度" 线性增长,是 batch 上限的真正瓶颈**,不是权重。
- 传统"连续整块按 max_len 预留"引发三种浪费:**内部碎片、外部碎片、预留浪费**,真实利用率常只有 20-40%。
- **PagedAttention = 给 KV Cache 做虚拟内存分页**:固定大小 block + block table(逻辑块→物理块)+ 按需分配。物理上不连续,逻辑上连续。
- 效果:内部碎片降到 ≤ block_size−1,外部碎片和预留浪费消失,利用率拉到 90%+。
- 额外红利:**prefix sharing、beam 共享、prefix caching**,靠 block table + 引用计数 + copy-on-write 实现。
- 代价:需要专门的 paged attention kernel(间接寻址,要小心访存合并)。
