## 1. 压测的正确姿势:控制变量

你做过大数据调优,深知「乱压一通的数据没法用」。LLM 压测尤其要控好变量,否则曲线会乱成一团。压测前先把这些钉死:

**输入变量(自变量):**
- **并发数(concurrency)**:同时在途的请求数。这是我们主要扫描的变量。
- **输入长度分布**:prompt 多长?要贴近真实业务(短问答 vs 长文档),因为 prefill 成本随输入长度涨。
- **输出长度分布**:生成多少 token?直接影响每请求耗时和 KV Cache 占用。

**采集指标(因变量):**
- 延迟:**TTFT、TPOT、E2E**,都要看 **P50 / P95 / P99**(回忆 Lesson 1,平均值骗人)。
- 吞吐:**output tokens/s**(核心)、QPS。
- 资源:GPU 利用率、显存占用。

> **黄金原则:压测负载必须贴近真实流量分布。** 用「全是 128 token 输入、生成 128 token」的均匀负载测出来的数,上线遇到真实的长短混合流量会被打脸。最好从线上日志采样真实的输入/输出长度分布来回放。这和你大数据压测「要用真实数据规模和倾斜分布」是一个道理。

压测工具有两类:**写脚本**(灵活,本课主力,见 `code/`)或用 **locust**(有 Web UI、自动统计分位数,适合团队共享)。两个我们都给。

## 2. 核心方法:吞吐-延迟曲线与拐点

这是容量规划的灵魂。做法:**固定输入/输出长度分布,逐步加大并发,记录每个并发下的(吞吐, P99 延迟),画成曲线。**

```
P99 延迟
  ▲
  │                                        ╱ ← 并发再加,延迟暴涨
  │                                      ╱     吞吐却几乎不再涨
  │                                  ╱        (系统已饱和,请求在排队)
  │                            ╱
  │                       ╱ ← ★ 拐点(knee)
  │                  ╱        延迟开始明显上翘,
  │             ╱             吞吐接近上限
  │       ╱  ← 线性区:延迟平稳,吞吐随并发线性增长
  │  ╱
  └──────────────────────────────────────────►  吞吐 (tokens/s)
```

三个区间,看懂了你就掌握了容量规划:

- **线性区(拐点前)**:并发增加,吞吐线性涨,延迟基本平稳。GPU 还没喂饱,系统很健康。
- **拐点(knee)**:延迟开始明显上翘的那个点。**此时吞吐接近系统极限,再加并发只会让延迟恶化而吞吐不涨。**
- **饱和区(拐点后)**:请求大量排队,延迟暴涨(主要是排队时间),吞吐到顶。**绝对不要让线上长期运行在这个区。**

> **核心结论:容量规划的目标,就是让线上稳态运行在「拐点附近、且满足 SLA」的位置。** 拐点给你「单卡(单副本)的最大可用吞吐」,SLA 给你「延迟红线」,两者取更严的那个,就是这张卡能安全承载的吞吐上限。这和你在 Spark 里找「并行度的甜点(再加 executor 就收益递减)」是完全一样的思路。

实操:并发从 1、2、4、8、16、32、64…倍增地扫,每个点压够时长(让系统进入稳态、统计量稳定),记录吞吐和 P99,画出来找那个「上翘点」。

## 3. GPU 监控:别被「利用率 100%」骗了

压测时必须同步盯 GPU,否则你不知道瓶颈在哪。最快的工具是 `nvidia-smi`:

```bash
# 每 1 秒刷新一次,实时看
nvidia-smi -l 1

# 只采关键字段,适合脚本/记录(CSV 格式)
nvidia-smi --query-gpu=timestamp,utilization.gpu,memory.used,memory.total,power.draw \
           --format=csv -l 1
```

几个关键指标和**新手最易踩的坑**:

| 指标 | 含义 | 怎么看 |
|---|---|---|
| `utilization.gpu` | GPU「忙」的时间占比 | ⚠️ **不等于算力被用满**,见下面警告 |
| `memory.used` | 显存占用 | 接近上限说明 KV Cache 快满,并发到顶 |
| `power.draw` | 实时功耗 | **更能反映真实算力利用**,接近 TDP 才是真忙 |
| SM occupancy | SM 实际占用率 | 要用 Nsight / DCGM 才能看到,最准 |

> **最大的坑:`utilization.gpu` = 100% 不代表算力跑满!** 它只表示「过去采样周期里,GPU 上有 kernel 在跑」的时间占比。哪怕只有一个小 kernel 在跑、SM 大量空闲,只要它一直在跑,利用率也显示 100%。**decode 阶段是带宽受限(Module 1 结论),算力其实没跑满,但 utilization 常年 100%。** 想知道是不是真的算力瓶颈,要看 **功耗是否接近 TDP** 和 **SM occupancy**(DCGM/Nsight),或者直接看「加大 batch 吞吐还涨不涨」。

生产监控用 NVIDIA 的 **DCGM(Data Center GPU Manager)** + `dcgm-exporter`,能导出 SM 活跃度、显存带宽利用率、Tensor Core 利用率等更细的指标到 Prometheus。

## 4. Prometheus + Grafana:最小监控栈

线上不能靠人盯 `nvidia-smi`,要有持久化的指标和告警。标准组合:

```
  推理服务 (vLLM /metrics)  ┐
  dcgm-exporter (GPU 指标)  ┼──▶ Prometheus ──▶ Grafana ──▶ 仪表盘 + 告警
  node-exporter (机器指标)  ┘    (拉取+存储)      (可视化)
```

- **Prometheus**:时序数据库 + 采集器。它**主动拉取(pull)**各个 `/metrics` 端点。你做过监控的话,这套 pull 模型很熟。
- **Grafana**:可视化,把 Prometheus 的数据画成仪表盘,配告警(P99 超阈值就报警)。
- **数据源**:
  - **vLLM 自带 `/metrics`**:启动 `vllm serve` 后访问 `http://host:8000/metrics`,直接暴露 Prometheus 格式的 TTFT、TPOT、吞吐、运行/等待队列长度、KV cache 使用率等——开箱即用,非常香。
  - **dcgm-exporter**:GPU 硬件指标。
  - **node-exporter**:CPU/内存/网络。

最小可跑的 `docker-compose.yml` 和 Prometheus 配置在 `code/monitoring/`,几条命令就能起一套。关键看板要放:**P99 TTFT、P99 TPOT、output tokens/s、running/waiting 队列长度、KV cache 使用率、GPU 功耗**。

> 这套和你大数据里的监控(指标采集→时序库→看板→告警)是同构的,概念可以直接迁移。唯一新增的是 **GPU 专属指标**(显存、SM、KV cache 使用率),它们才是 LLM 服务的命脉。

## 5. 容量规划:从 SLA 算出要几张卡

这是本课的终极目标,也是面试压轴题。把前面的压测结果变成「要买几张卡」。分四步:

### 第一步:定 SLA 和流量预估
- SLA 示例:**P99 TTFT < 2s,P99 TPOT < 100ms**。
- 流量预估:高峰期 **每秒 R 个请求**,平均每请求输入 `L_in` token、输出 `L_out` token。

### 第二步:压测得到「单副本可用吞吐」
用 §2 的方法,在**满足 SLA 的前提下**(不是饱和点,是 SLA 红线和拐点取严者),测出单个副本(1 张卡或 1 个 TP 组)能承载的**最大吞吐** `C`(单位:output tokens/s,或满足 SLA 的最大并发)。

> 注意:要用满足 SLA 的吞吐,不是峰值吞吐。峰值吞吐往往已经在饱和区、P99 爆表。

### 第三步:算需求总吞吐
- 需求 output 吞吐 ≈ `R × L_out`(tokens/s)。
- (prefill 侧用 `R × L_in` 校验是否会成为瓶颈,长输入业务尤其要算。)

### 第四步:算卡数(别忘了余量)

> **副本数 N = ⌈ 需求总吞吐 / 单副本可用吞吐 C ⌉ × 余量系数**

```
   N = ceil( (R × L_out) / C ) × 安全余量(1.3~1.5)

   总卡数 = N × 每副本卡数(单卡模型=1;TP=2 则每副本 2 张)
```

安全余量(1.3~1.5)用来吸收:流量波动、突发高峰、滚动发布时少一个副本、长尾请求。**和你大数据里「按峰值 + buffer 配资源」完全一样。**

### 完整算例(吃透它)

> 业务:聊天服务。SLA:P99 TTFT<2s。高峰 **R=20 req/s**,平均输出 `L_out=200` token。压测(7B 模型,单张 A100)测得:满足 SLA 时单卡可用吞吐 **C=1500 output tokens/s**。
>
> - 需求吞吐 = 20 × 200 = **4000 tokens/s**
> - 副本数 N = ⌈4000 / 1500⌉ = ⌈2.67⌉ = **3**
> - 加 1.4 余量 = 3 × 1.4 ≈ 4.2 → **5 个副本**
> - 7B 单卡放得下,每副本 1 张卡 → **共 5 张 A100**
>
> 如果换 70B 模型、每副本要 TP=4(4 张卡),同样算出 N=5,则总卡数 = 5×4 = **20 张**。这就是为什么大模型烧钱——容量规划一算就知道。

> **降本反推**:这个公式也告诉你优化的价值。把 C 翻倍(靠量化 FP8 / 换 TRT-LLM / 调 batch),卡数直接砍半。这就是 Module 5 量化和 Lesson 2 TRT-LLM 的商业意义——**单卡吞吐 C 每提升一点,都是真金白银的卡钱。**

<details>
<summary>参考答案</summary>

1. 因为 prefill 成本随输入长度涨、KV Cache 和总耗时随输出长度涨,长短请求在 continuous batching 里的相互影响也不同。用均匀固定长度测,无法暴露真实流量里「长请求拖慢短请求」「长输出撑爆 KV Cache」等问题,测出的吞吐和 P99 会过于乐观,上线被真实的长短混合 + 倾斜流量打脸。

3. **不能**。utilization=100% 只表示采样周期内一直有 kernel 在跑,不代表 SM/算力被用满(decode 带宽受限时常年 100% 但算力没满)。进一步判断:看**功耗是否接近 TDP**、用 **DCGM/Nsight 看 SM occupancy 和显存带宽利用率**,或直接「加大 batch 看吞吐还涨不涨」——还能涨说明没真饱和。
4. 需求吞吐 = 30 × 150 = 4500 tokens/s。N = ⌈4500/2000⌉ = ⌈2.25⌉ = 3,× 1.4 ≈ 4.2 → **5 张**(7B 单卡,每副本 1 张)。
5. C=3500 时:N = ⌈4500/3500⌉ = ⌈1.29⌉ = 2,× 1.4 = 2.8 → **3 张**。从 5 张省到 3 张,**省 2 张**。说明**单卡吞吐 C 的优化(量化/换引擎/调 batch)直接等比例转化为卡钱**,这是推理优化的核心商业价值。
6. 同构步骤:定 SLA/目标 → 用代表性负载压测得单位资源能力 → 按需求总量除以单位能力 → 加安全余量 → 得资源数。LLM 独有的约束是 **GPU 显存(KV Cache)对并发的硬限制**,以及延迟分 TTFT/TPOT 两段(prefill 算力受限、decode 带宽受限),这是大数据(主要受 CPU/内存/shuffle 约束)没有的维度。

## 小结

- 压测要**控制变量**(并发、输入/输出长度分布)、**采集 P50/P95/P99** 的 TTFT/TPOT/E2E 和 token 吞吐,负载必须**贴近真实流量分布**。
- 核心方法是**吞吐-延迟曲线**:逐步加并发,找**拐点(knee)**——延迟开始上翘、吞吐到顶的点。容量规划让线上稳态运行在「拐点附近且满足 SLA」处。
- 监控 GPU 用 `nvidia-smi`,但记住 **utilization=100% 不等于算力满**(decode 带宽受限),要结合**功耗、SM occupancy**(DCGM/Nsight)判断真实瓶颈。
- 生产监控用 **Prometheus(拉取)+ Grafana(看板/告警)**,数据源:vLLM `/metrics`、dcgm-exporter、node-exporter;核心看板:P99 TTFT/TPOT、output tokens/s、队列长度、KV cache 使用率、GPU 功耗。
- 容量规划公式:**N = ⌈(R×L_out)/C⌉ × 余量(1.3~1.5)**,总卡数 = N × 每副本卡数。**单卡吞吐 C 的优化直接等比例省卡钱**——这就是量化和换引擎的商业意义。
