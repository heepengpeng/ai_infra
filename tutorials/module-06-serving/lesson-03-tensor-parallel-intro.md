## 1. 先算账:显存到底差多少

别上来就并行,先搞清「为什么必须并行」。一个模型推理时显存被三块吃掉:

```
推理显存 ≈ 模型权重 + KV Cache + 激活/临时缓冲
            (固定,最大头)  (随并发&序列长度涨)  (相对小)
```

**权重显存**的估算公式(背下来,面试常考):

> 权重显存(字节)≈ 参数量 × 每参数字节数。FP16 = 2 字节/参数,FP8/INT8 = 1 字节,INT4 = 0.5 字节。

举例(只算权重):

| 模型 | 参数量 | FP16 权重 | 单卡能否放下(80G A100) |
|---|---|---|---|
| 7B | 70 亿 | ~14 GB | ✅ 轻松,还剩很多给 KV Cache |
| 13B | 130 亿 | ~26 GB | ✅ 可以 |
| 70B | 700 亿 | ~140 GB | ❌ **一张 80G 都不够**,必须多卡 |
| 405B | 4050 亿 | ~810 GB | ❌ 要十几张卡 |

加上 KV Cache 和激活,实际需求还要更高。**结论很清楚:7B/13B 单卡能跑,70B 以上必须把模型切到多卡。** 量化能缓解(70B INT4 ≈ 35GB,单卡勉强),但超大模型和高并发场景,多卡是绕不开的。

> 类比你的分布式经验:这就像一份数据单机内存装不下,必须 sharding 到多个节点。区别在于,模型的「分片」之间**计算上强耦合**(一层的输出是下一层的输入,矩阵乘横跨分片),所以通信比大数据的 shuffle 还要频繁、还要低延迟。

## 2. 两种切法:张量并行 vs 流水线并行

把模型摊到多卡,有两个正交的维度。先建立全局观:

```
模型(很多层 Transformer Block 堆叠)

流水线并行 PP(竖着切,按层分):          张量并行 TP(横着切,层内每个矩阵分):
 ┌──────────┐                            ┌──────────────────────┐
 │ Layer 0-9 │ → GPU0                     │ Layer 0: 权重矩阵被切成   │
 ├──────────┤                            │ GPU0 | GPU1 | GPU2 | GPU3 │
 │ Layer10-19│ → GPU1                     │ 每张卡算一部分,再合并    │
 ├──────────┤                            │ Layer 1: 同样切 4 份      │
 │ Layer20-29│ → GPU2                     │ ...                      │
 ├──────────┤                            │ 每一层都要跨卡通信合并    │
 │ Layer30-39│ → GPU3                     └──────────────────────┘
 └──────────┘
 数据像流水线一样依次流过各卡            每一层内部,所有卡并肩算同一层
```

- **流水线并行(Pipeline Parallel, PP)**:**按层切**。GPU0 放前 10 层,GPU1 放中间 10 层……数据像工厂流水线一样依次流过。卡间通信少(只在切分点传一次激活),但有「流水线气泡」(后面的卡要等前面的卡先算完),且天然引入延迟。适合**跨机器**(机间带宽低,通信少才划算)。
- **张量并行(Tensor Parallel, TP)**:**层内切**。把每一层里的大矩阵(权重)按行/列切成 N 份,每张卡算 1/N,**每一层都要把各卡的部分结果合并**。通信极频繁,但能真正把单层的计算和显存都摊开。适合**单机多卡**(机内 NVLink 带宽极高,扛得住频繁通信)。

> 一句话区分:**PP 是「接力跑」(按层串行流过,通信少、有气泡),TP 是「并肩抬」(层内一起算,通信多、无气泡)。** 生产里大模型常常 **TP + PP 混用**:机内用 TP(吃 NVLink 高带宽),机间用 PP(省通信)。本课聚焦更常用、更需要理解通信的 TP。

## 3. 张量并行怎么切:为什么 Transformer 天生适合

TP 的精髓是 **Megatron-LM** 提出的切法,它聪明地利用了矩阵乘的结构,让通信次数降到最少。我们看 Transformer 里两个主要计算块怎么切。

### 3.1 FFN(MLP)块:列切 + 行切,一个 AllReduce 搞定

FFN 是 `Y = GeLU(X · A) · B`,两个矩阵乘。Megatron 的切法:

```
X(输入,每卡都有完整副本)
   │
   ├── A 按【列】切: A = [A1 | A2]      (GPU0 拿 A1, GPU1 拿 A2)
   │     GPU0: Y1 = GeLU(X · A1)        ← 各算各的,无需通信
   │     GPU1: Y2 = GeLU(X · A2)
   │
   ├── B 按【行】切: B = [B1; B2]       (GPU0 拿 B1, GPU1 拿 B2)
   │     GPU0: Z1 = Y1 · B1             ← 各算各的,得到部分和
   │     GPU1: Z2 = Y2 · B2
   │
   └── Z = Z1 + Z2   ←★ 这一步需要 AllReduce!把两卡的部分和加起来
```

**关键洞察**:第一个矩阵按列切、第二个按行切,这样中间结果 `Y1/Y2` 不需要通信(各卡自己留着用),只有最后把部分和 `Z1+Z2` 合并时,才需要**一次 AllReduce**。整个 FFN 块只通信一次。

### 3.2 Attention 块:按「头」切,天然并行

多头注意力本来就是多个独立的 head,**切头是最自然的**:

```
多头注意力有 32 个 head(以 32 头为例),TP=4:
   GPU0 算 head 0-7    ┐
   GPU1 算 head 8-15   │  每张卡独立算自己负责的 head 的 QKV、attention
   GPU2 算 head 16-23  │  (head 之间本就独立,无需通信)
   GPU3 算 head 24-31  ┘
        │
   输出投影 O 按行切,最后 AllReduce 合并 ←★ 同样一次 AllReduce
```

每个 head 的 Q/K/V 投影、attention 计算都是独立的,各卡算自己的头;最后输出投影合并时一次 AllReduce。

> **结论**:Transformer 的一个完整 layer(attention + FFN),在张量并行下只需 **2 次 AllReduce**(attention 出口一次、FFN 出口一次)。这就是为什么 TP 在 Transformer 上如此高效——但「每层 2 次」累加起来,层数一多通信就很可观,这正是下一节要算的代价。

## 4. NCCL 与 AllReduce:多卡怎么对齐结果

切开计算后,卡间要交换数据。NVIDIA 的 **NCCL(NVIDIA Collective Communications Library)** 就是干这个的——它提供 GPU 间的**集合通信原语**,你做分布式一定见过它们的 MPI 版本:

| 原语 | 作用 | TP 里的用途 |
|---|---|---|
| **AllReduce** | 所有卡的数据按元素求和(或其他规约),结果广播回每张卡 | **TP 的主力**,合并部分和 |
| AllGather | 收集每张卡的分片,拼成完整张量,每卡都拿到全量 | 某些切分方式收集结果 |
| ReduceScatter | 规约后把结果分片散给各卡 | AllReduce 的「半步」 |
| Broadcast | 一张卡的数据复制给所有卡 | 分发权重/输入 |

### 4.1 AllReduce 是怎么实现的(Ring AllReduce)

理解它的代价,要看它的经典实现 **Ring AllReduce**。N 张卡组成一个环,数据切成 N 块:

```
4 张卡的环:GPU0 → GPU1 → GPU2 → GPU3 → (回到)GPU0

阶段一 ReduceScatter(N-1 步):每张卡把一块数据传给下一张并累加,
  转一圈后,每张卡持有「某一块」的最终求和结果。
阶段二 AllGather(N-1 步):再转一圈,把各自的最终块传播给所有卡。

总通信量:每张卡收发 ≈ 2 × (N-1)/N × 数据量,与卡数 N 几乎无关 → 带宽高效
```

> 关键性质:**Ring AllReduce 的每卡通信量几乎不随卡数增长**(约等于 2 倍数据量),所以带宽利用率高、可扩展性好。这是它成为分布式训练/推理标配的原因。你在大数据里见过的 reduce 思想是一样的,只是这里跑在 GPU 显存 + NVLink/PCIe/网络上。

### 4.2 通信开销:为什么 TP 几乎只在机内用

TP 的命门是:**每生成一个 token,每一层都要做 2 次 AllReduce,通信和计算严格串行**(必须等结果合并才能进下一层)。所以通信链路的带宽和延迟直接决定 TP 的效率。

```
通信链路带宽对比(数量级):
  NVLink(机内卡间)      : ~数百 GB/s ~ 900 GB/s   ✅ TP 的乐土
  PCIe(机内无 NVLink)   : ~16-64 GB/s             △ TP 勉强,效率打折
  以太网/IB(跨机)       : ~10-50 GB/s 且延迟高     ❌ TP 会被通信拖死
```

> **黄金法则:张量并行尽量只在单机内、有 NVLink 的卡之间做。** 跨机的 TP 会让 AllReduce 走慢速网络,通信时间远超计算时间,GPU 大量空等——这时该换成通信更少的流水线并行(PP)或数据并行(多副本)。这和你在分布式系统里「让高频通信留在机架内、跨机只走低频同步」的直觉完全一致。

通信开销还意味着 TP **不是线性加速**:TP=2 不会让吞吐翻倍,因为多出了 AllReduce 的时间。TP 的首要价值是**「让放不下的模型放得下」**,其次才是加速;卡数越多,通信占比越高,边际收益递减。

## 5. 怎么选并行策略(决策表)

把前面的取舍汇总成一张实战决策表:

| 情况 | 推荐策略 | 理由 |
|---|---|---|
| 模型单卡放得下(7B/13B) | **不并行**,多卡就开**多副本(数据并行)** | 没有通信开销,吞吐线性扩展 |
| 模型单卡放不下,单机多卡(有 NVLink) | **张量并行 TP** | NVLink 扛得住频繁 AllReduce |
| 模型超大,要跨多机 | **TP(机内)+ PP(机间)** | 机内吃 NVLink 高带宽,机间用低通信的 PP |
| 想提吞吐而非装下模型 | 优先**多副本**,不够再 TP | 多副本无通信、扩展性最好 |

> 记住优先级:**能不并行就不并行(多副本最划算)→ 装不下才 TP(且尽量机内)→ 单机装不下才上 PP/跨机。** 并行度越高、跨得越远,通信税越重。

## 6. 动手实验:用 vLLM 跑张量并行

> 需要 AutoDL 多卡实例(2×4090 或 2×A100)。**先确认卡间互联**:`nvidia-smi topo -m` 看是 NV#(NVLink)还是 PHB/PXB(走 PCIe)。有 NVLink 体验最好。

vLLM 把张量并行封装得极简,一个参数 `tensor_parallel_size` 搞定。脚本在 `code/`。

### 实验 A:单卡 vs 双卡 TP,看显存与可行性(必做)

先看一个**单卡放不下、TP 后放得下**的对比。用一个稍大的模型(如 14B,单张 24G 4090 放不下 FP16):

```bash
cd code
# 单卡尝试加载 14B(预期显存不足 OOM,体会「装不下」)
python tp_serve.py --model Qwen/Qwen2.5-14B-Instruct --tp 1

# 双卡张量并行(模型被切成两半,各占一张卡,成功加载)
python tp_serve.py --model Qwen/Qwen2.5-14B-Instruct --tp 2
```

加载成功后,另开终端在每张卡上跑 `nvidia-smi`,观察**模型权重被均摊到两张卡**(每卡显存占用约为单卡的一半)。

### 实验 B:观察 TP 不是线性加速(必做)

用一个两张卡都放得下的模型(如 7B),分别用 TP=1 和 TP=2 起服务,用 Lesson 1 的 `load_client.py`(或 Lesson 4 的压测脚本)压同样的负载,对比吞吐:

```bash
python tp_serve.py --model Qwen/Qwen2.5-7B-Instruct --tp 1 --port 8001
# 换一个终端 / 重启:
python tp_serve.py --model Qwen/Qwen2.5-7B-Instruct --tp 2 --port 8002
```

记录两者的 token 吞吐。**你会发现 TP=2 的吞吐远达不到 2 倍**(通常 1.2~1.7 倍,取决于 NVLink/PCIe 和模型大小),这就是 AllReduce 通信税。在 PCIe-only 的机器上差距更明显——亲手验证 §4.2 的结论。

5. 你有 8 张卡,要部署一个单卡放得下的 7B 模型,目标是最大吞吐。你会用 TP=8 吗?应该怎么部署?
6. (开放)把 TP 的 AllReduce 和你在分布式训练/大数据里见过的 reduce 操作对比,它们在「通信量与节点数的关系」上有什么共同的优化思想?

<details>
<summary>参考答案</summary>

1. 70B × 2 字节 ≈ **140 GB**,一张 80G 卡光权重就放不下。即使能放,推理还要 **KV Cache**(随并发和序列长度增长,高并发下可能几十 GB)和**激活/临时缓冲**,所以 70B 必须多卡(或重度量化)。
2. 因为这样能让**中间结果不需要通信**:列切第一个矩阵,各卡算出的 `Y1/Y2` 是完整中间张量的不同列,正好对应行切的第二个矩阵 `B1/B2`,各卡 `Yi·Bi` 得到部分和,**只需最后一次 AllReduce** 合并。若切法不匹配,中间就要额外通信。好处:整个 FFN 只通信一次。
3. **80 次**。每层 2 次(attention 出口 1 次 + FFN 出口 1 次),40 层 × 2 = 80 次 AllReduce(decode 阶段每个 token 都要走一遍)。
4. 因为 TP 每层 2 次 AllReduce,通信和计算严格串行、极其频繁。NVLink(几百 GB/s)扛得住;跨机走以太网/IB(带宽低一两个数量级、延迟高),AllReduce 时间会远超计算时间,GPU 大量空等,加速比崩溃。所以高频通信要留在机内。
5. **不用 TP=8**。7B 单卡放得下,应该开 **8 个副本(数据并行)**,每副本占 1 张卡,前面挂负载均衡。这样**无通信开销、吞吐近线性扩展到约 8 倍**;TP=8 反而引入大量 AllReduce、吞吐远不到 8 倍且浪费。结论:能装下就用多副本。
6. 共同思想是 **Ring/树形规约让每节点通信量不随节点数线性增长**(Ring AllReduce 每节点约 2 倍数据量,与 N 几乎无关),从而带宽高效、可扩展。无论是 GPU 间 NCCL 还是大数据的分布式 reduce,核心都是「避免某个节点成为汇聚瓶颈,把通信均摊到环/树上」。

## 小结

- 大模型显存主要被**权重**吃掉(FP16 ≈ 参数量×2 字节),70B 以上单卡放不下,**必须把模型切到多卡**。
- 两种切法:**流水线并行 PP(按层切,接力跑,通信少有气泡,适合跨机)** 和 **张量并行 TP(层内切,并肩抬,通信多无气泡,适合机内)**。
- TP 的 Megatron 切法巧妙利用矩阵结构:**一个 Transformer layer 只需 2 次 AllReduce**(attention + FFN 各一次),attention 按头切、FFN 列切+行切。
- **NCCL 提供集合通信**,主力是 **AllReduce**(Ring 实现,每卡通信量几乎不随卡数增长)。但 decode 时每层每 token 都要 AllReduce,**通信和计算串行**,所以 **TP 几乎只在机内 NVLink 上用,跨机会被通信拖死**。
- 选型优先级:**能不并行就多副本 → 装不下才 TP(机内)→ 单机装不下才 PP/跨机**。TP 不是线性加速,首要价值是「让放不下的放得下」。
- vLLM 用 `tensor_parallel_size` 一参搞定 TP,对调用方透明。
