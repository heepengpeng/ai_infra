## 1. 一个类比:跑车 vs 大巴

设想要把 1000 个人从 A 城送到 B 城。

- **CPU = 一辆超级跑车**:速度极快(单趟很快),但一次只能坐 2 个人。它的设计哲学是"让单个任务尽可能快地完成"——这叫**低延迟(low latency)**。
- **GPU = 一队大巴**:单辆大巴比跑车慢,但有几百辆、每辆能坐 50 人。它的设计哲学是"单位时间内运完尽可能多的人"——这叫**高吞吐(high throughput)**。

如果任务是"送 1 个 VIP 尽快到达",跑车赢。
如果任务是"送 1000 个人,总时间最短",大巴队赢。

**深度学习就是"送 1000 个人"**:一次矩阵乘法里有几百万个互相独立的乘加运算,它们可以同时算。这正是 GPU 的主场。

## 2. 从晶体管预算看本质差异

芯片面积(晶体管)是有限的,CPU 和 GPU 把预算花在了不同地方:

```
CPU 的晶体管预算:                    GPU 的晶体管预算:
┌─────────────────────────┐         ┌─────────────────────────┐
│  少量超强 ALU(计算单元) │         │  海量 ALU(计算单元)     │
│  ███                     │         │  ████████████████████    │
│                          │         │  ████████████████████    │
│  巨大的缓存 Cache        │         │  ████████████████████    │
│  ██████████████          │         │  小缓存 ██               │
│  复杂控制逻辑            │         │  简单控制逻辑 █          │
│  (分支预测/乱序执行)    │         │                          │
└─────────────────────────┘         └─────────────────────────┘
   为"单线程快"服务              为"成千上万线程并行"服务
```

- **CPU**:把大量晶体管用于**缓存**和**控制逻辑**(分支预测、乱序执行、预取),目的是让少数几个线程跑得飞快、不被内存延迟拖慢。
- **GPU**:把绝大多数晶体管用于**算术单元(ALU)**,控制逻辑和缓存都很精简。它不怕内存延迟——因为它有成千上万个线程,一批线程在等内存时,硬件立刻切换去算另一批线程,**用并行度掩盖延迟**。

> 记住这句话:**CPU 用缓存对抗延迟,GPU 用并行对抗延迟。** 这是两种架构哲学的根本分水岭。

## 3. SIMT:GPU 的执行模型

CPU 多核是 MIMD(多指令多数据,每个核干自己的事)。GPU 是 **SIMT(Single Instruction, Multiple Threads,单指令多线程)**。

含义:GPU 把线程按 **32 个一组**打包,这一组叫一个 **warp(线程束)**。一个 warp 里的 32 个线程**在同一时刻执行同一条指令**,只是各自处理不同的数据。

为什么是 32?这是 NVIDIA 硬件的调度粒度。理解 warp 极其重要,因为它直接影响性能,后面会反复遇到两个关键点:

- **分支发散(warp divergence)**:如果一个 warp 里有的线程走 `if`、有的走 `else`,硬件只能先让走 if 的执行(else 的线程闲置等待),再让走 else 的执行。两条分支被**串行化**,性能砍半。所以 kernel 里要尽量避免同一 warp 内的线程走不同分支。
- **访存合并(coalescing)**:如果一个 warp 的 32 个线程访问的是**连续**的内存地址,硬件能把它们合并成一次大的内存事务,效率最高;如果访问地址东一个西一个,就要拆成很多次小访问,带宽浪费严重。

这两点你现在记住名字和直觉即可,Module 1 后面有专门的课动手验证。

## 4. 内存:GPU 真正的瓶颈

新手以为 GPU 慢是因为"算得不够快",**其实大部分时候瓶颈是内存带宽,不是算力。**

GPU 的内存分好几层,从快到慢、从小到大:

```
寄存器 Register      —— 每线程私有,最快,极少量(ns 级)
   ↓
共享内存 Shared Mem  —— 一个 block 内线程共享,很快,几十~上百 KB(片上)
   ↓
L2 Cache            —— 全芯片共享
   ↓
全局显存 Global Mem  —— 就是那 24GB/80GB 显存,容量大但相对慢(几百 ns 延迟)
```

一个关键事实:从全局显存读一个数,延迟可能是做一次浮点乘法的**几百倍**。所以高性能 kernel 的核心套路就是:

> **把数据从慢的全局显存搬到快的共享内存/寄存器,尽量复用,减少对全局显存的访问次数。**

你在大数据里做的"减少 Shuffle、内存复用"优化,思想完全一样,只是换了硬件层级。这是你的可迁移优势。

## 5. Roofline:判断瓶颈到底在哪

一个简单但极有用的性能模型。横轴是**计算强度**(每读 1 字节数据能做多少次浮点运算,FLOP/Byte),纵轴是**实际能达到的算力**(FLOP/s)。

```
算力 FLOP/s
  ▲
  │                 ┌──────────────  ← 屋顶:峰值算力(算力受限区)
  │                /
  │              /  ← 斜坡:被内存带宽限制(带宽受限区)
  │            /
  │          /
  └────────────────────────────►  计算强度 FLOP/Byte
```

- 如果你的 kernel 落在**斜坡上(带宽受限)**:优化方向是减少访存、提高数据复用。
- 如果落在**屋顶下(算力受限)**:优化方向是提高计算效率(用 Tensor Core、减少冗余计算)。

大模型推理里,**decode 阶段几乎总是带宽受限**(每生成一个 token 要把整个模型权重读一遍,但计算量很小),这就是为什么"量化"(减少要读的字节数)能显著加速 decode——这是后面量化模块的核心动机,现在先埋个伏笔。

## 6. 什么计算适合 GPU?

✅ **适合**:
- 大量**独立**、**相同**的运算(矩阵乘、卷积、逐元素操作)。
- 数据规模大(小数据 GPU 启动开销都赚不回来)。

❌ **不适合**:
- 强**串行依赖**(后一步必须等前一步,无法并行)。
- 大量**分支**、不规则控制流。
- 频繁 CPU-GPU 数据来回拷贝的小任务(传输开销吃掉收益)。

深度学习的训练和推理,主体是大矩阵运算,天然契合 GPU。

## 思考练习(不用写代码,想清楚即可)

1. 为什么说"GPU 不怕内存延迟"?它靠什么掩盖延迟?
2. 一个 warp 里 32 个线程执行 `if (threadId % 2 == 0) A() else B()`,会发生什么?性能受什么影响?
3. 大模型 decode 阶段为什么是"带宽受限"而不是"算力受限"?
4. 你在 Spark 里做过"谓词下推减少 Shuffle",它和 GPU 里"减少全局显存访问"在思想上有什么共通点?

<details>
<summary>参考答案(想完再看)</summary>

1. 靠**海量线程 + 硬件零开销切换**:一批线程等内存时,调度器立刻切到另一批就绪的线程去计算,计算和访存重叠(overlap),延迟被"藏"起来了。
2. 发生 **warp divergence**:偶数线程先执行 `A()`(奇数线程闲置),再奇数线程执行 `B()`(偶数闲置),两条路径被串行化,这个 warp 的有效吞吐大约减半。
3. 因为每生成 1 个 token,需要把模型**全部权重**从显存读进来用一次,数据搬运量巨大,但实际只算了 1 个 token 的乘加,计算量很小 → 计算强度低 → 卡在带宽上。
4. 共通点都是 **减少昂贵的数据移动**:Shuffle 是跨节点网络搬数据(贵),全局显存访问是跨片内存搬数据(相对贵),优化思路都是"让数据少搬、就近复用、提前过滤"。

</details>

## 小结

- GPU 是**吞吐优先**架构:大量 ALU + 海量线程,用并行掩盖延迟。
- 执行单位是 **warp(32 线程)**,要警惕 **分支发散** 和 **访存不合并**。
- 性能瓶颈**常在内存带宽而非算力**,核心优化是**减少全局显存访问、复用数据**。
- 用 **roofline** 判断瓶颈类型;大模型 decode 是带宽受限,这是量化加速的根源。
