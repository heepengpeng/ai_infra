# M1 · Lesson 6:共享内存与线程协作

> 前 5 课的线程都是"原子化的个体":各算各的、互不通信。但真正高性能的 kernel(归约、转置、矩阵乘)靠的是**一个 block 内的线程像一个小团队那样协作**——把数据搬进高速的共享内存,反复复用,再一起写回。本课讲透这个机制:`__shared__`、`__syncthreads()`、以及一个隐蔽的性能陷阱 bank conflict。
> 预计用时:2.5 小时。
> 前置:Lesson 1(内存层级、warp)、Lesson 4(五层内存,shared 是片上高速内存)、Lesson 5(cudaEvent 计时)。

## 学习目标

1. 理解共享内存是什么、为什么快,会用 `__shared__` 声明并在 block 内共享数据。
2. 掌握 `__syncthreads()`:为什么必须同步、漏写会怎样、放错位置(在分支里)会死锁。
3. 理解 shared memory 的 **bank(存储体)** 结构和 **bank conflict**,会用 padding 避免。
4. 建立"**分块(tiling)**"思想:为什么"搬进 shared → 复用 → 写回"是高性能 kernel 的通用套路。

## 1. 共享内存:block 内线程的"公共白板"

回顾 Lesson 4 的内存层级:共享内存(shared memory)是**片上(on-chip)**的高速内存,速度接近寄存器,延迟比全局显存低**一两个数量级**。它的关键特性:

> **共享内存的作用域是一个 block。** 同一个 block 内的所有线程看到同一块共享内存、能互相读写;不同 block 之间各有各的,互不可见。

打个比方:

```
全局显存 = 公司的中央档案室(大、慢、所有人共用,来回跑很费时)
共享内存 = 你们小组桌上的一块白板(小、快、仅本组可见可写)
寄存器   = 你自己手里的草稿纸(最快,只有你自己能看)

高性能套路:别每次都跑去档案室查一个数。
          组长把这次要用的一批资料从档案室搬到白板上(一次),
          组内所有人在白板上反复算(很多次),算完再把结果送回档案室(一次)。
```

这个"搬到白板、反复用、送回去"正是 Lesson 1 说的"减少全局显存访问、复用数据",也是你大数据经验里"把热数据缓存到内存、别反复读磁盘"的同构思想。

声明方式有两种:

```cpp
// 静态:编译期已知大小
__shared__ float tile[256];

// 动态:大小在启动时由第三个 <<<grid, block, sharedBytes>>> 参数给定
extern __shared__ float tile[];
// 启动: kernel<<<grid, block, 256 * sizeof(float)>>>(...);
```

## 2. 一个会出错的例子:为什么需要 `__syncthreads()`

设想:让一个 block 的每个线程读自己位置的数据到共享内存,然后**每个线程要读它"右边邻居"的数据**(比如做差分)。

```cpp
__shared__ float s[256];
int t = threadIdx.x;
s[t] = input[blockIdx.x * blockDim.x + t];   // 各线程把自己那份搬进白板
// 危险!此刻别的线程可能还没写完它的 s[t+1]
float right = s[t + 1];                       // 读邻居 —— 可能读到垃圾!
```

问题在哪?**一个 block 的线程不是同时执行的**——它们按 warp(32 个一组)被调度,warp 之间有先后。当 `t=0` 的线程想读 `s[1]` 时,负责写 `s[1]` 的线程(在另一个 warp 里)可能还没执行到那行。这是典型的**数据竞争(race condition)**。

解决:在"大家都写完"和"开始读别人的"之间插一道**屏障(barrier)**:

```cpp
__shared__ float s[256];
int t = threadIdx.x;
s[t] = input[blockIdx.x * blockDim.x + t];
__syncthreads();          // 屏障:等本 block 所有线程都到这里,才一起放行
float right = s[t + 1];   // 现在能保证 s[t+1] 已被写入
```

`__syncthreads()` 的语义:

> **block 内所有线程都执行到这一行后,才一起继续往下走。** 它是 block 内线程协作的"集合点"。注意:它只同步**同一个 block** 内的线程,不能跨 block 同步(跨 block 同步要靠 kernel 结束)。

## 3. `__syncthreads()` 的致命陷阱:别放在分支里

这是新手最隐蔽的 bug。`__syncthreads()` 要求**block 内每个线程都能到达它**。如果你把它放进一个**并非所有线程都进入**的分支,没进分支的线程永远到不了屏障,到了屏障的线程就**永远等下去——死锁(挂死)**。

```cpp
// 错误!t<128 的线程进 if 撞到屏障等待,t>=128 的线程根本不进 if,
// 永远不会到达屏障 → 整个 block 卡死。
if (threadIdx.x < 128) {
    s[threadIdx.x] = ...;
    __syncthreads();        // ✗ 死锁
}

// 正确:让屏障对所有线程都可达
if (threadIdx.x < 128) {
    s[threadIdx.x] = ...;
}
__syncthreads();            // ✓ 所有线程都能到
```

> 铁律:**`__syncthreads()` 必须在所有线程都会执行到的位置**(通常放在分支外)。同理,基于 `threadIdx` 提前 `return` 的线程后面也不能再有别的线程依赖的屏障。这条踩过的人都记一辈子。

## 4. Bank Conflict:共享内存内部还有"车道"

共享内存快,但有个内部结构要懂,否则"快"会打折。共享内存被分成 **32 个 bank(存储体)**,可以理解成 32 条并行车道。地址按 4 字节(一个 float)为单位**轮流**分到这 32 个 bank:

```
地址(float下标):  0   1   2  ...  31  | 32  33  ... 63 | 64 ...
落到的 bank:       0   1   2  ...  31  |  0   1  ... 31 |  0 ...
（每 32 个 float 循环一遍）
```

规则:**一个 warp 的 32 个线程,如果同一拍访问的地址正好落在 32 个不同的 bank,就能一次并行完成(全速);如果有 2 个或以上线程访问同一个 bank 的不同地址,这些访问被串行化,叫 bank conflict。**

(一个例外:如果一个 warp 的多个线程读**同一个地址**,硬件会广播,不算冲突。冲突特指"同 bank、不同地址"。)

最常见的冲突场景:按**列**访问一个二维共享数组。

```cpp
__shared__ float tile[32][32];
// warp 内 32 个线程都取第 0 列:tile[0][tx], tile[1][tx]... 不对,看下面
// 设 tx 固定、ty=threadIdx.x 变化,访问 tile[ty][0]:
//   tile[0][0] 在 bank 0, tile[1][0] 在 float 下标 32 → bank 0,
//   tile[2][0] 下标 64 → bank 0 ... 32 个线程全撞 bank 0 → 32 路冲突,慢 32 倍!
```

经典解法:**padding(填充)**,把每行多开一列,打乱对齐:

```cpp
__shared__ float tile[32][33];   // 多一列!行宽变 33(不是 32 的倍数)
// 现在 tile[0][0]→bank0, tile[1][0]→下标33→bank1, tile[2][0]→下标66→bank2 ...
// 32 个线程恰好落在 32 个不同 bank,冲突消失。只浪费一点点共享内存。
```

> 这个 `[32][33]` 的小技巧在 Lesson 8 矩阵转置里会再次出现——那是 bank conflict 最经典的实战。现在记住:**当一个 warp 按"跨 bank 步长正好是 32 的倍数"访问共享内存时,会发生冲突,加一列 padding 是标准解药。**

## 5. 完整范例:用共享内存做"邻域滑动平均"

把上面的概念串成一个完整 kernel(完整代码见 `code/shared_stencil.cu`):每个输出元素 = 自己和左右邻居三个数的平均(1D stencil)。朴素写法每个元素要从全局显存读 3 次,且相邻线程读的数据**大量重叠**;用共享内存,每个数据**只从全局读一次**,放进白板,大家复用。

```cpp
__global__ void smooth3(const float* in, float* out, int n) {
    // +2 是为左右各留一个"halo(光环)"边界元素
    __shared__ float s[256 + 2];
    int gid = blockIdx.x * blockDim.x + threadIdx.x;
    int t = threadIdx.x;

    // 主体:每个线程把自己那份搬进 s 的中间区域(下标 +1 给左 halo 让位)
    if (gid < n) s[t + 1] = in[gid];
    // 让 block 的 0 号、末号线程顺便把左右 halo 也搬进来
    if (t == 0)            s[0]               = (gid > 0)     ? in[gid - 1] : in[0];
    if (t == blockDim.x-1) s[blockDim.x + 1]  = (gid + 1 < n) ? in[gid + 1] : in[n-1];

    __syncthreads();   // 屏障:确保白板(含 halo)全部写好再开始读

    if (gid < n) {
        // 全部从快速的共享内存读,不再碰全局显存
        out[gid] = (s[t] + s[t + 1] + s[t + 2]) / 3.0f;
    }
}
```

要点回顾:**搬入(全局→shared)→ `__syncthreads()` → 计算(只读 shared)→ 写回(shared→全局)**。这个"搬入—同步—计算—写回"四段式,就是接下来归约(L7)和转置(L8)的骨架。

## 练习题

1. 为什么 `__syncthreads()` 不能跨 block 同步?如果两个 block 之间真的需要同步,该怎么办?
2. 下面这段为什么可能死锁?怎么改?
```cpp
if (threadIdx.x % 2 == 0) { __syncthreads(); }
```
3. `__shared__ float tile[32][32]`,一个 warp 的 32 个线程访问 `tile[threadIdx.x][0]`,会有几路 bank conflict?改成 `[32][33]` 后呢?
4. 共享内存这么快,为什么不把所有数据都放进去?它有什么限制?
5. 用你的话说清"搬入—同步—计算—写回"四段式为什么能提速(从访存次数角度)。

<details>
<summary>参考答案</summary>

1. 因为不同 block 可能被调度到不同 SM、且不保证同时驻留(有的 block 可能要等前面的跑完才开始),硬件层面无法让它们集合。跨 block 同步的标准做法是**把 kernel 拆成两个**——第一个 kernel 结束就是一个全局同步点,第二个 kernel 再继续(L7 多级归约就这么做)。
2. 只有偶数线程进入 `if` 并撞上屏障,奇数线程不进 `if`、永远到不了屏障,偶数线程会永远等下去 → 死锁。改法:把 `__syncthreads()` 移到 `if` 外,让所有线程都能到达。
3. `tile[t][0]` 的 float 下标是 `t*32`,32 个线程全部落在 bank 0 → **32 路冲突**(慢约 32 倍)。改成 `[32][33]` 后下标是 `t*33`,33 与 32 互质,32 个线程落到 32 个不同 bank → **0 冲突**。
4. 共享内存**容量很小**(每 block 几十~上百 KB,且和 occupancy 挂钩:一个 block 用得越多,SM 上能同时驻留的 block 越少)。只适合放当前 tile 要反复复用的小块热数据,放不下整个大数组。
5. 朴素写法每个数据被多个线程从**全局显存**重复读(stencil 里一个数被 3 个输出用到 → 读 3 次);四段式让每个数据**只从全局读一次**进 shared,后续复用都在高速 shared 上完成,把昂贵的全局访存次数降到最低——这正是 Lesson 1"减少全局显存访问、复用数据"的落地。

</details>

## 小结

- 共享内存是**片上高速内存,作用域为一个 block**,是 block 内线程协作的"公共白板"。
- 线程间通过共享内存通信时,必须用 **`__syncthreads()`** 屏障避免数据竞争;它**只同步本 block**,且**必须放在所有线程都可达的位置**(分支里会死锁)。
- 共享内存分 **32 个 bank**,一个 warp 内多线程访问同 bank 不同地址会 **bank conflict 被串行化**;二维数组按列访问最易触发,**加一列 padding(如 `[32][33]`)** 是标准解药。
- 高性能 kernel 的通用骨架:**搬入(全局→shared)→ 同步 → 计算(复用 shared)→ 写回**。
