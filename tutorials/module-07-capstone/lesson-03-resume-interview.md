### 板块一:GPU 架构与 CUDA 基础

**Q1. GPU 为什么比 CPU 适合深度学习?**
要点:CPU 是**低延迟**架构(少量强 ALU + 大缓存 + 复杂控制),为单线程快服务;GPU 是**高吞吐**架构(海量 ALU + 海量线程),用并行掩盖延迟。深度学习主体是大矩阵乘,海量独立乘加,契合 GPU。一句深入:**CPU 用缓存对抗延迟,GPU 用并行对抗延迟。**

**Q2. 什么是 warp?warp divergence 和访存合并是什么?**
要点:GPU 以 **32 线程为一组(warp)**,SIMT 模型,同一 warp 同一时刻执行同一指令。**divergence**:同 warp 内线程走不同分支,被串行化,性能下降。**coalescing**:同 warp 的 32 线程访问连续地址,合并成一次内存事务,带宽利用最高。一句深入:写 kernel 要避免同 warp 分支发散、保证访存连续。

**Q3. GPU 的存储层级?为什么说优化常常是"内存优化"?**
要点:寄存器 → 共享内存(片上,block 内共享)→ L2 → 全局显存(HBM,大但慢)。从全局显存读一个数的延迟是一次浮点乘法的几百倍。一句深入:**多数 kernel 是访存瓶颈而非算力瓶颈**,核心套路是把数据搬到共享内存/寄存器复用,减少全局访存——这正是 FlashAttention 的核心思想。

**Q4. roofline 模型怎么用?**
要点:横轴计算强度(FLOP/Byte),纵轴可达算力。斜坡区=**带宽受限**(优化方向:减少访存、提高复用);屋顶下=**算力受限**(优化方向:用 Tensor Core、减少冗余计算)。一句深入:**LLM 的 decode 阶段几乎总是带宽受限**(每个 token 要把全部权重读一遍,计算量却小),这是量化能加速 decode 的根本原因。

### 板块二:核心算子

**Q5. 矩阵乘(GEMM)怎么优化?**
要点:**分块(tiling)**把子块load 进共享内存复用,减少全局访存;**寄存器分块**进一步复用;**向量化访存**(float4);用 **Tensor Core**(WMMA/MMA)。一句深入:GEMM 优化的核心矛盾就是提升计算强度,让 kernel 从带宽受限挪到算力受限。

**Q6. 什么是算子融合?为什么有用?**
要点:把多个连续算子(如 matmul+bias+activation)合成一个 kernel,**避免中间结果写回再读全局显存**,减少 kernel launch 开销和访存。一句深入:对带宽受限的逐元素/norm 类算子收益最大——这正是我在 SDXL 优化里用过的手段。

**Q7. FlashAttention 解决了什么问题?核心思想?**
要点:朴素 attention 要把 N×N 的注意力矩阵物化到显存,显存 O(N²) 且大量 HBM 读写。FlashAttention 用 **tiling + online softmax**,分块计算、不物化完整矩阵,在 SRAM 里累积,**把显存复杂度降到 O(N)、大幅减少 HBM 访问**。一句深入:它是典型的 **IO-aware** 算子,不减少计算量但减少了访存,所以在带宽受限场景大幅加速。

**Q8. online softmax 为什么能避免数值溢出且可分块?**
要点:softmax 要减最大值防溢出。online 方式**边遍历边维护当前最大值和累积和**,新块来了用缩放因子修正之前的结果,无需一次看到所有元素。一句深入:这让 attention 能 streaming 地分块算,是 FlashAttention 可行的数学基础。

### 板块三:LLM 推理机制(重中之重)

**Q9. prefill 和 decode 有什么区别?各自的瓶颈?**
要点:**prefill**:并行处理整个 prompt,一次算多个 token,**算力受限**(compute-bound),GPU 利用率高。**decode**:自回归逐个生成,每步只算 1 个 token 但要读全部权重 + KV Cache,**带宽受限**(memory-bound),GPU 利用率低。一句深入:两阶段特性相反,这就是为什么要 chunked-prefill、为什么 decode 是优化重点、为什么 batching 对 decode 收益巨大。

**Q10. 什么是 KV Cache?为什么需要?显存怎么算?**
要点:自回归生成时,每个新 token 的 attention 要用到之前所有 token 的 K、V。**缓存住已算过的 K/V,避免每步重算**,用空间换时间。显存 ≈ `2(K,V) × layers × seq_len × num_kv_heads × head_dim × dtype_bytes × batch`。一句深入:KV Cache 随序列和并发线性增长,常常**比模型权重还占显存**,是长上下文/高并发的主要瓶颈——这就是 PagedAttention 和 KV 量化要解决的。

**Q11. 什么是 PagedAttention?解决什么问题?**
要点:传统 KV Cache 要**连续大块显存**,导致严重**内部/外部碎片**和过度预留(按 max_len 分配)。PagedAttention 借鉴 OS 虚拟内存分页:**把 KV Cache 切成固定大小的 block,按需分配,用块表映射逻辑→物理**。一句深入:几乎消除碎片,显存利用率从 ~20–40% 提到 >90%,从而能塞更多并发请求,还天然支持前缀共享(copy-on-write)。

**Q12. 什么是 Continuous Batching(连续批处理)?和静态 batching 的区别?**
要点:**静态 batching**:整批一起开始、一起结束,先生成完的请求要干等最慢的(GPU 空转)。**Continuous Batching**(迭代级调度):**每个迭代步**重新组 batch,完成的请求立刻退出、释放资源,新请求随时加入。一句深入:它把 GPU 持续喂满,是 vLLM 吞吐高的首要原因——我 Capstone 里 8× 增益主要来自它。

**Q13. 投机解码(speculative decoding)原理?**
要点:用一个**小的草稿模型**快速生成多个候选 token,再用**大模型一次并行验证**这些 token(把多步 decode 变成一次 prefill 式的并行前向),接受匹配的部分。一句深入:它利用了"decode 带宽受限、并行验证几乎免费"的特性,在不损失输出分布(可做无损验证)的前提下加速 decode,尤其适合大模型 + 高接受率场景。

**Q14. GQA / MQA 是什么?为什么用?**
要点:MHA 每个 query head 有独立 K/V head;**MQA** 所有 query head 共享 1 组 K/V;**GQA** 折中,分组共享。一句深入:减少 K/V head 数 → **直接减小 KV Cache 显存和 decode 的访存量**,对带宽受限的 decode 是重要优化,几乎不掉点。Qwen/Llama 都用 GQA。

### 板块四:量化

**Q15. 量化为什么能加速推理?**
要点:把权重(和/或激活)从 FP16 降到 INT8/INT4/FP8。两个收益:**显存↓**(放更多模型/更大 KV Cache/更多并发)、**访存量↓**(decode 带宽受限,读更少字节 = 更快)。一句深入:量化对 **decode 加速明显**(带宽受限),对 prefill(算力受限)收益相对小,除非有低精度 Tensor Core 算力加成。

**Q16. PTQ 和 QAT 区别?推理岗常用哪个?**
要点:**PTQ**(训练后量化):不重训,用少量校准数据定标度,快、便宜。**QAT**(量化感知训练):训练中模拟量化,精度更好但成本高。推理部署主流是 **PTQ**(GPTQ/AWQ 都是 PTQ)。一句深入:权衡是精度 vs 成本,服务化部署绝大多数选 PTQ。

**Q17. GPTQ 的核心思想?**
要点:逐层量化,基于**二阶信息(Hessian)**,量化每个权重时调整**尚未量化的权重**来补偿误差(OBQ/OBS 思路),逐列处理。一句深入:它把"量化误差"在层内重新分配以最小化输出误差,所以 INT4 下仍能保住精度。

**Q18. AWQ 的核心思想?和 GPTQ 区别?**
要点:AWQ 观察到**少量"显著权重"(由激活幅度判定)对精度影响最大**,通过**逐通道缩放**保护这些重要通道,再量化。一句深入:AWQ 不需要反向/Hessian,更快、对指令模型友好,部署常用;GPTQ 靠误差补偿,AWQ 靠保护显著通道,两者都属 PTW(weight-only)INT4 主流方案。

**Q19. FP8 和 INT8 有什么不同?为什么 FP8 越来越火?**
要点:INT8 是均匀量化;**FP8(E4M3/E5M2)有指数位,动态范围大**,对激活中的离群值(outlier)更友好。Hopper/Ada 有 FP8 Tensor Core 硬件加速。一句深入:FP8 能在**激活也量化**时较好保精度(激活离群值是 INT8 的痛点,SmoothQuant 就是为解决它),且有硬件算力红利。

**Q20. 什么是 KV Cache 量化?**
要点:把 KV Cache 也量化(如 FP8/INT8 存储),**减小 KV 显存占用** → 支持更长上下文 / 更多并发。一句深入:长上下文场景 KV Cache 是显存大头,量化它收益显著,代价是少量精度损失,vLLM 用 `--kv-cache-dtype fp8` 即可开启。

### 板块五:分布式推理

**Q21. 张量并行(TP)和流水线并行(PP)区别?**
要点:**TP**:把单个算子(如 GEMM、attention)**在权重维度切分**到多卡,每卡算一部分,通过 **all-reduce/all-gather** 合并;通信频繁(每层都通信),适合卡间高带宽(NVLink)。**PP**:把模型**按层切分**成多段放不同卡,像流水线传递激活;通信少但有 **流水线气泡(bubble)**,靠 micro-batch 缓解。一句深入:单机多卡优先 TP(NVLink 快);跨机或卡多到 TP 通信吃不消时叠加 PP。

**Q22. NCCL 是什么?常见集合通信操作?**
要点:NVIDIA 的多 GPU 集合通信库。常见:**all-reduce**(各卡数据规约后广播,TP 必用)、**all-gather**、**reduce-scatter**、**broadcast**。一句深入:TP 的瓶颈往往在 all-reduce 通信量,所以对卡间带宽(NVLink/IB)敏感;通信和计算 overlap 是优化重点。

**Q23. 为什么有时单卡放得下也要多卡?**
要点:① 提高吞吐(更多算力/带宽);② 降低单请求延迟(TP 把单层计算分摊);③ 给 KV Cache 腾显存以支持更长上下文/更高并发。一句深入:不是"放不下才多卡",而是"延迟/吞吐/上下文长度"的工程权衡。

**Q24.(可选)什么是 PD 分离(Prefill-Decode 分离)?**
要点:prefill(算力受限)和 decode(带宽受限)特性相反,放一起会互相干扰。**PD 分离**把两阶段部署到不同实例/卡,各自用最优配置和并行策略,通过传 KV Cache 衔接。一句深入:这是较新的进阶架构(vLLM/SGLang 都在推进),能同时优化 TTFT 和吞吐,体现你跟进前沿。

---

### 板块六:推理服务指标与系统

**Q25. 衡量推理服务的核心指标有哪些?**
要点:**吞吐**(tokens/s,成本视角)、**TTFT**(首 token 延迟,体感)、**TPOT/ITL**(token 间延迟,流式顺滑)、**P50/P99 端到端延迟**(SLA)、**显存/并发容量**。一句深入:**吞吐和延迟通常此消彼长**,优化目标是"在满足延迟 SLA 的前提下最大化吞吐",这也是容量规划的核心。

**Q26. 怎么做一次可信的推理 benchmark?**
要点:**预热**(排除 CUDA 初始化/编译)、**同步**(`torch.cuda.synchronize`,否则测的是发指令时间)、**多次取中位数/百分位**、固定输入分布、报告并发与 request-rate。一句深入:不 sync、不预热是新手假数据的最大来源——我 Capstone 严格遵守这套(可迁移自我大数据压测经验)。

**Q27. 如何定位一个推理服务"变慢了"?**
要点:分层排查:先看是 TTFT 还是 TPOT 变差 → GPU 利用率/显存(`nvidia-smi`)→ 是不是 KV Cache 满了导致请求排队/抢占 → 用 **Nsight Systems/Compute** 看 kernel 级瓶颈 → 看 batch 是否被喂满。一句深入:方法论和我大数据调优一致——先量化现象、分层定位、再改一个变量验证。

**Q28. chunked prefill 解决什么问题?**
要点:长 prompt 的 prefill 很重,会**长时间占住 GPU,阻塞其他请求的 decode**,导致 TPOT 抖动/TTFT 变长。chunked prefill 把长 prefill **切成小块**,和 decode 交错调度。一句深入:它平滑了 prefill 对 decode 的干扰,是 prefill/decode 在同一实例共存时的关键调度优化。

## 4. 项目讲解话术与常见追问

八股是"广度",项目讲解是"深度"。面试官会挑你简历里一个项目深挖到底。**准备好 2 个能讲 10 分钟、接得住追问的项目**:首推 Capstone,次选 SDXL 10×。

### 4.1 万能讲解结构(STAR 变体:背景→目标→方法→结果→反思)

```
1. 一句话定位:这是个什么项目,我的角色,最终结果(先抛数字)
2. 背景与挑战:为什么要做,难在哪(瓶颈在哪)
3. 我的方法:做了哪几件事,每件事为什么有效(讲原理!)
4. 结果与权衡:量化收益 + 我付出的代价 + 怎么权衡的
5. 反思:踩了什么坑、学到什么、还能怎么做更好(诚实=加分)
```

### 4.2 Capstone 讲解范例(60 秒电梯版)

> "我独立做了一个把 Qwen2.5-7B 推理吞吐优化 14× 的项目。起点是 HuggingFace 朴素推理,我先严格测了 baseline——预热、同步、取中位数。然后分四步优化,每步单独测量收益:第一步换 vLLM,靠 Continuous Batching 把 GPU 喂满 + PagedAttention 解决 KV Cache 碎片,这一步贡献了最大的约 8×;第二步上 AWQ 量化,显存降 60%,decode 带宽受限所以提速明显,我同时做了精度护栏,CEval 子集只掉 1 个点;第三步扫调度参数,画吞吐-延迟曲线找 SLA 内最优。全程有复现 repo 和博客。"

### 4.3 高频追问与应对

| 追问 | 应对要点 |
|---|---|
| "这 14× 里每项贡献多少?" | 拿出**收益归因表**,逐项报增量(这就是 Lesson 1 让你做归因的原因)。 |
| "为什么 continuous batching 能涨这么多?" | 讲 decode 带宽受限 + 静态 batching 的 GPU 空转 → CB 迭代级调度喂满 GPU。 |
| "PagedAttention 到底解决什么?" | 讲 KV Cache 碎片 + 过度预留 → 分页按需分配 → 显存利用率 >90% → 更多并发。 |
| "量化为什么对 decode 帮助大,对 prefill 小?" | decode 带宽受限(读更少字节就更快),prefill 算力受限(除非有低精度算力红利)。 |
| "你怎么保证测的数据是真的?" | 讲 benchmark 纪律:预热/sync/中位数/固定输入/报百分位。 |
| "如果让你再优化一倍,你怎么做?" | speculative decoding、KV Cache FP8、TP 多卡、自定义 Triton 算子——挑一个讲思路。 |
| "你没做过 LLM,凭什么能做好?" | 用 2.1–2.3 的迁移叙事:SDXL 推理优化 + Tachyons 系统优化 + 大数据减少数据移动,**性能优化方法论跨域验证过**。 |

### 4.4 SDXL 项目讲解要点(证明能力可迁移)

讲 SDXL 时,**主动把它和 LLM 挂钩**:"DiT/UNet 和 Transformer 在算子层是相通的——都是 GEMM、attention、norm。我在 SDXL 上做的算子融合、低精度、profiling、跨框架精度对齐,方法论可以直接迁移到 LLM 推理。" 这样面试官就不会觉得"扩散模型经验和这岗位无关"。

### 4.5 讲解的三个禁忌

- ❌ **只报结果不讲原理**:"我用了 vLLM 就快了" → 显得只会调包。要讲清为什么快。
- ❌ **夸大/含糊数字**:数字一定要能复现、能解释口径。被追问口径答不上来=信任崩塌。
- ❌ **回避局限**:假装项目完美。主动说"speculative decoding 我留作后续没做完"反而显得诚实、有判断力。
